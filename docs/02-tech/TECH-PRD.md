## 1. 产品概述

Glean 是一个给自己和朋友用的技术碎片记录库。核心动作只有一个：想到什么就记一条，不分类、不打草稿，几秒钟存进去。这些碎片平时看起来是流水账，但通过标签汇聚、全文搜索和相关推荐，会慢慢长出一个个主题页；写到某个主题时，一键把这些碎片按时间导出成 Markdown，就是一篇博客的原料。

它要解决的不是"知识管理"这个大词，而是三件具体的小事：记的时候不要因为要分类而放弃，找的时候不要因为散落在聊天记录和书签里而放弃，写东西的时候不要因为想不起来用过而重头再来。

## 2. 目标用户

| 角色 | 说明 | 技术背景 | 使用频率 |
|------|------|---------|---------|
| 记录者 A | 产品的主要提出者，负责后端方向，日常在电脑前开发与部署 | 开发者，熟悉命令行、数据库与接口调试 | 每天多次 |
| 记录者 B | 合作的朋友，负责前端方向，同样会遇到踩坑与链接收集 | 开发者，熟悉页面开发与浏览器调试 | 每天多次 |

两人共用同一份内容，互相可见。不做注册开放、不做成员邀请、不做权限分级。

## 3. 问题与痛点

- 当前做法：
  - 踩坑时随手发到微信收藏或文件传输助手，看到好文章就加进浏览器书签，命令和配置贴在备忘录里；
  - 试过用笔记类工具做知识库，建了目录、套了模板；
  - 写博客时凭记忆去翻，翻不到就重写一遍。
- 主要问题：
  - 散落各处，事后按关键词找不回来，等于没存；
  - 记录动作本身有摩擦（要打开页面、选分类、起标题），于是干脆不记，同样的坑重踩；
  - 笔记工具的分类与模板维护成本高于收益，坚持不过两周；
  - 记完之后从不回看，原料与成品之间断了链。
- 不解决的后果：
  - 时间被重复消耗在已经解决过的问题上；
  - 想写的东西写不出来，因为素材在三个月前就已经丢了；
  - 两个人各自踩各自的坑，经验不共享。

## 4. 典型使用场景

### 场景 1：调试中途顺手记一条

- 时机：工作日白天，正在调试一个部署问题时
- 终端：电脑浏览器
- 主体：记录者 A
- 流程：在页面上按下快捷键，输入框获得焦点 → 输入一句"nginx 反代 websocket 要加 Upgrade 头" → 回车 → 该条立即出现在首页时间流最上方，类型被自动判为"踩坑" → 全程不离开当前页面，不选分类、不写标题。整个过程从开始打字到看见结果在 10 秒以内。

### 场景 2：手机上刷到文章随手存

- 时机：通勤或休息时刷到一篇有价值的文章
- 终端：手机浏览器（已添加到主屏）
- 主体：记录者 B
- 流程：打开应用 → 把文章链接粘贴进输入框 → 系统识别出这是一个链接 → 点保存 → 链接以"链接"类型入库，显示域名与链接地址，点击可跳转到原站点。系统不抓取网页内容，标题如需保留由用户自行写在内容里。

### 场景 3：写博客时集中翻旧碎片

- 时机：周末准备写一篇关于缓存设计的文章
- 终端：电脑浏览器
- 主体：记录者 A
- 流程：进入标签页，点"redis"标签 → 看到该标签下按时间倒序排列的全部碎片（来自两个人的）→ 点开其中几条看详情与"相关碎片" → 觉得素材够了，点"导出 Markdown" → 得到一份按时间排序、带标签与来源链接的文本 → 复制到自己的博客编辑器里继续写。

### 场景 4：找一条记不清的旧内容

- 时机：突然要用某个几天前记下的命令
- 终端：电脑或手机
- 主体：两个人中任意一个
- 流程：进搜索页输入印象里的关键词"gradle 离线" → 结果列表出现若干条，含"gradle 离线编译一直失败"那条 → 叠加标签"部署"进一步缩小 → 点开详情，复制命令。若无结果，页面提示"试试别的关键词"，并给出一键清空筛选。

## 5. 输入定义

| 输入项 | 来源 | 提供方 | 格式 | 频率 |
|--------|------|--------|------|------|
| 碎片内容 | 手动录入（单行输入框，回车提交） | 记录者 A / B | 纯文本，允许含代码与换行 | 每天多次 |
| 碎片类型 | 手动选择，可留空由系统推测 | 记录者 A / B | 五选一：链接 / 命令·代码 / 踩坑 / 想法 / 流程 | 每次记录 |
| 标签 | 手动输入，可留空，从历史标签补全 | 记录者 A / B | 扁平文本标签，0～3 个 | 每次记录 |
| 链接地址 | 手动粘贴或随内容带出 | 记录者 A / B | http / https 地址 | 每次记录 |
| 账号登录 | 手动输入 | 记录者 A / B | 账号口令 | 首次登录，此后保持 30 天 |

补充约定：

- 必填项只有"内容"一项。类型、标签、链接均可留空，先存后补。
- 当整条内容本身就是一个 http(s) 地址时，系统自动按"链接"类型处理，并从地址中解析出域名用于列表展示。
- 系统不对链接发起任何网络请求，不抓取标题、摘要或正文。
- 类型留空时由系统按内容推测：整条为链接 → 链接；含代码块或命令行特征 → 命令·代码；其余 → 想法。保存后可在详情页改。
- 标签为扁平结构，不做层级；输入时从历史标签中补全。
- 验收指标：从开始打字到碎片出现在列表里，不超过 10 秒；登录态保持 30 天，不因重新登录而阻断记录。

## 6. 输出定义

| 输出项 | 形式 | 呈现位置 | 受众 | 是否需导出 |
|--------|------|---------|------|-----------|
| 首页时间流 | 倒序列表 + 顶部快速输入框 | 屏幕 | 记录者 A / B | 否 |
| 活跃热力图 | 按天计数、类似 GitHub 的方格图 | 屏幕 | 记录者 A / B | 否 |
| 标签页 | 标签云 + 该标签下碎片时间线 | 屏幕 | 记录者 A / B | 否 |
| 搜索结果 | 关键词命中列表 + 标签组合筛选 | 屏幕 | 记录者 A / B | 否 |
| 单条详情 | 内容、类型、标签、作者、相关碎片、编辑入口 | 屏幕 | 记录者 A / B | 否 |
| 随机漫游 | 随机抽取 5 条旧碎片 | 屏幕 | 记录者 A / B | 否 |
| 主题 Markdown 草稿 | 文本 | 屏幕（可复制）/ 文件 | 记录者 A / B | 是，Markdown |

补充约定：

- 每条碎片在列表与详情页标出作者与创建时间。
- 导出范围可以是全部碎片，也可以是某个标签下的碎片；按时间排序，含内容、标签与来源链接；系统只产出文本，不负责发布。
- 热力图只反映"哪天记了几条"的活跃度，不承担知识库本体的职责。

## 7. 验收标准

- [ ] 连续 14 天内，每天至少有 1 条碎片入库；该结果可通过"按创建日期分组计数"直接统计验证。
- [ ] 任意一条超过一周的旧碎片，可通过一个记忆中存在的关键词在搜索结果中被找到。
- [ ] 从在输入框打第一个字到该碎片出现在时间流中，耗时不超过 10 秒（在已登录、页面已打开的前提下计时）。
- [ ] 粘贴链接后保存成功，列表中以域名作为该条的展示标识，链接地址可点击跳转到原站点，全程不出现阻断性报错。
- [ ] 两人分别登录后看到的时间流内容完全一致，且每条碎片都能看出是谁记的。
- [ ] 任一标签页可一键导出为 Markdown 文本，内容按时间排序且包含该标签下的全部碎片。

## 8. 本版范围外

| 不做的事 | 原因 | 后续是否纳入 |
|---------|------|-------------|
| 周期性回顾（每周/每月新增统计） | 需先积累足够碎片才有意义 | 会做，排 V2 |
| AI 生成的周期摘要 | 锦上添花，非本版必需 | 会做，排 V2 |
| 双链 `[[标签]]` 式互相引用 | 对技术碎片而言"相关推荐"性价比更高 | 暂不做 |
| 推送到博客后台直接发布 | 导出 Markdown 已能满足"复制走"的需求 | 暂不做 |
| 开放注册、邀请、权限分级 | 固定两人共用一份内容，无此需求 | 永久不做 |
| 评论、点赞等互动 | 双人自用，无社交需求 | 永久不做 |
| 复杂富文本编辑器 | 与"10 秒记一条"的目标直接冲突 | 永久不做 |
| 多级分类树 | 分类应由标签事后涌现，不应在输入时前置 | 永久不做 |

### 8.1 后续版本路线图

| 版本 | 内容 | 触发条件 |
|------|------|---------|
| V1 | 记录、轻标签、全文搜索、相关推荐、热力图、随机漫游、导出 Markdown、双人共享与作者标识 | 现在 |
| V2 | 周期性回顾（每周/每月新增 N 条、涉及主题）、AI 周期摘要 | V1 连续跑满两周、每天都有碎片入库之后（即验收标准第 1 条达成） |

已约定的后续版本约束记录于此，防止后续版本偏离：

- 任何后续版本均不得引入输入时的强制分类或强制标签，输入必须保持"一个输入框 + 回车"。
- 任何后续版本均不得把热力图解释为知识库本体，它只表示活跃度。
- 若未来引入 AI 摘要，摘要须标注为机器生成，且不得替代原始碎片。
- 数据库中的每条碎片须始终保留作者字段，即便界面上不展示。

## 9. 异常与边界处理

| 情况 | 期望行为 |
|------|---------|
| 数据为空 | 首页显示引导句"记下第一条"，输入框自动获得焦点；标签页、热力图、随机漫游在无数据时给出同一类空状态提示，不报错 |
| 搜索无结果 | 提示"试试别的关键词"，并提供一键清空关键词与标签筛选的操作 |
| 数据格式错误 | 输入内容为空或只有空白时不允许提交，其余内容一律照存，不做格式校验拦截 |
| 处理过程中出错 | 保存失败时保留已输入内容不清空，提示"保存失败，请重试" |
| 数据量超出预期 | 时间流、搜索结果、标签页均分页加载；热力图按天聚合只取计数，不因碎片总量增长而变慢 |
| 网络中断 | 提示"网络异常，内容已暂存在本地"，恢复后提示重试；用户已输入的文字不得丢失 |
| 链接无法访问 | 碎片照常保存，链接原样保留，列表以域名作为展示标识；系统不探测链接是否可访问，不做失效提示 |
| 两人同时编辑同一条 | 后保存者收到"这条刚被对方改过"的提示，由本人决定是否覆盖 |
| 尝试删除对方的碎片 | 界面上不提供该入口；不出现权限报错页 |
| 同一链接被两人重复记录 | 两条都保留，不做自动去重，仅可在详情页看到"相关碎片"里出现同一链接 |

## 10. 约束条件

| 类型 | 约束 |
|------|------|
| 时间 | 无交付死线 |
| 预算 | 低成本自部署，开销控制在单台云主机量级，不引入付费第三方服务 |
| 平台 | 浏览器形态，电脑与手机均可用；手机端可添加到主屏并以接近应用的方式打开 |

### 12. 各决策点定案

#### 决策点 1：数据存储与全文检索

- 决定：既有 MySQL 8 之上，使用 InnoDB `FULLTEXT` 索引 + `ngram` 中文分词实现全文检索。
- 理由：两人自用、每年数千条，无需独立检索服务；`FULLTEXT` 同时提供中文分词与相关度打分，满足"旧碎片可被关键词找到"的验收标准，并为"相关碎片"提供相似度依据；不引入双写一致性风险与额外常驻进程。
- 未采用：`LIKE %关键词%`（无分词、无相关度打分、全表扫描）；Meilisearch / Elasticsearch（能力过剩，需额外安装、开机自启、独立备份，且存在双写不一致风险）。
- 代价 / 风险：建表须写 `WITH PARSER ngram`；`innodb_ngram_token_size` 默认 2 且为只读启动参数，改动须重建索引；单字关键词无法命中，须由应用层回退 `LIKE` 兜底；中文停用词按内置规则，须用真实数据验证一次。

#### 决策点 2：登录与会话

- 决定：自写 JWT 鉴权过滤器，不引入 Spring Security 过滤器链。
- 理由：PRD 明确永久不做注册、邀请与权限分级，Security 的角色能力全部用不上，反引入过滤器链排障成本；JWT 无状态，服务重启不掉线，满足 30 天免登录。
- 未采用：Spring Security + JWT（能力过剩、排障成本高）；Session + Cookie（服务重启即掉线，与 30 天要求冲突）。
- 代价 / 风险：密码须用 BCrypt；token 签发、过期校验、`userId` 注入、CORS 预检放行均须自行实现；签名密钥不得提交进 git（骨架中 `application-dev.yml` 已明文含数据库密码，须一并改为环境变量）；JWT 无法主动失效。

#### 决策点 3：前端 UI 形态

- 决定：组件库方案，选定 Ant Design Vue 4.2.6，页面结构自行编写，不引入模板或 SSR 框架。
- 理由：用户前端为弱项并要求"尽量少写"，分页、消息提示、标签补全、筛选面板均属组件库强项；手机端高频动作仅"记一条""搜一条"，输入框 + 列表 + 栅格足够；热力图任何方案都需自绘。
- 未采用：Element Plus（用户明确排除）；Tailwind + 无头组件（上手成本与"少写"目标相反）；Vant 4（桌面端观感打折，而场景 3 在电脑上）；Nuxt / 现成模板（与既有 Vite 骨架冲突，SSR 无收益）。
- 代价 / 风险：`ant-design-vue` 4.2.6 发布于 2024-11，latest 长期未更新，生态会逐渐落后；须覆盖主题变量贴近轻量工具观感；窄屏须自写媒体查询，时间流禁用 `a-table`；须按需引入控制体积。

#### 决策点 4：链接的处理方式

- 决定：不抓取链接内容。只保存 URL，列表以解析出的域名作展示标识，点击跳转原站点。
- 理由：用户明确要求"直接留一个链接，我自己点进去就好"；抓取需承担 SSRF 防护、反爬降级、超时控制与无头浏览器常驻内存，收益仅是可被标题关键词搜索，在两人自用且可用标签替代的场景下不划算。去掉抓取后服务端不对任意外部地址发起请求，SSRF 风险整体消失。
- 未采用：轻量 `<title>` 抓取；静态抓取 + Playwright 兜底；Jsoup / Hutool 静态抓取。
- 代价 / 风险：未打标签的纯链接碎片只能通过 URL 或域名被搜索到，正文关键词搜不到，这是本决策主要的功能损失，须由标签习惯补足；系统不探测链接是否可访问，失效链接不提示。
- 连带需求变更：PRD 升至 v0.2（场景 2、输入定义表、补充约定、验收标准第 4 条、异常表、术语表）。

#### 决策点 5："相关碎片"推荐算法

- 决定：纯 SQL 加权打分，一次查询返回。`score = 标签交集数 × 3 + MATCH(内容) AGAINST(关键词) 相关度 × 时间衰减`；时间衰减为 30 天内 ×1.0、90 天内 ×0.5、更早 ×0.2；排除自身，取 top 5。
- 理由：PRD 已把排序依据写死为三要素，本质是加权公式；相关度可直接取自决策 1 的 `MATCH ... AGAINST`；数千条数据下 SQL 一次扫描无压力；用户要求"先做简单的"；可解释，调参有据。
- 未采用：Java 内存计算（过度设计，逻辑拆两处维护）；词向量 / 向量数据库（需引入 embedding 服务或本地模型，与拒绝重资产的方向冲突，结果不可解释）。
- 代价 / 风险：只对字面相关有效（"缓存"与"cache"互不推荐）；权重为初始经验值，须用真实数据校准；单字词无法参与相关度计算。

#### 决策点 6：部署与运行方式

- 决定：单进程部署。前端 `dist` 打包进后端 jar 静态资源，云主机 `java -jar` 运行，由内嵌 Tomcat 同时提供页面与接口。不引入 Nginx，不引入 Docker。
- 理由：用户选择最简方案，只要一个进程、一条启动命令，不维护反向代理与容器编排。该选择可逆：应用只监听 HTTP，日后在其前面加一层 Caddy 或 Nginx 即可，应用代码与构建产物无需改动。
- 未采用：Nginx + systemd（需维护两份配置，用户判断当前不需要）；Docker Compose（为两人自用引入容器层与数据卷备份心智负担）。
- 代价 / 风险：**手机"添加到主屏"在 iOS 与 Android 上实际要求 HTTPS**，无反向代理时该能力可能受限，缓解路径为后续前置一层 Caddy；静态资源缓存头与 gzip 须在 Spring 侧显式开启；重启期间数秒不可用；服务崩溃后不自恢复，须以 systemd 等方式托管进程（仅托管，不加反向代理）；应用端口直接暴露，暴露面略大。

#### 决策点 7：第三方依赖治理

- 决定：统一治理。删除 pom 中 `HikariCP` 显式版本（交 Boot 管理 6.3.3）；`fastjson 1.2.83` 换 `fastjson2 2.0.66`；`Hutool 5.8.44` 升 5.8.48；`MyBatis-Flex 1.11.1` 升 1.11.8。
- 理由：用户在"最小干预"与"统一治理"间最终选择后者，一次排掉可预见隐患；当前业务代码为空，迁移成本处于最低点；`HikariCP` 4.x 与 Boot 3.5 管理的 6.3.3 属明确版本错配，必须修正。
- 未采用：最小干预（已作废，见决策记录中的"决策 7"）；移除 fastjson 统一用 Jackson。
- 代价 / 风险：`fastjson` → `fastjson2` 包名由 `com.alibaba.fastjson` 变为 `com.alibaba.fastjson2`，import 须全量调整，否则编译失败；`MyBatis-Flex` 跨 7 个小版本，须重点回归分页、`FULLTEXT` 相关度查询与实体映射，并验证 `map-underscore-to-camel-case: false` 的既有行为；须复测 CI 中的 `mvn clean verify` 与 H2 上下文；仍不得开启 fastjson2 的 `autoType`。

### 13. 部署与运行方式

- 运行环境：单台云主机（Linux），本机开发环境为 Windows + 本地 MySQL 8.0.44
- 启动方式：`java -jar` 启动单个 jar（前端构建产物已打包进其静态资源目录）；建议以 systemd 托管进程实现开机自启与崩溃拉活，但不引入反向代理
- 数据存放位置：既有 MySQL 实例，库名 `glean`（由骨架遗留的 `lilac-blog` 改名）；数据库账号口令与 JWT 签名密钥一律通过环境变量注入，不再写死在 `application-dev.yml`
- 备份方式：`mysqldump` 每日一次，保留最近 7 份，落盘位置不与数据库数据目录同盘；恢复步骤写入 `README.md`
- 更新方式：本地 `mvn package` 产出 jar 后上传，替换旧 jar 并重启进程；更新选低峰时段，重启期间数秒不可用
- 访问方式：直接访问应用端口（默认 9090，`context-path=/api`）。**注意**：前端 `vite.config.ts` 现有 `rewrite: path.replace(/^\/api/, '')` 与后端 `context-path=/api` 叠加会导致 404，须在实现阶段统一为"保留 `/api` 前缀"，具体见第 17 节陷阱清单

### 15. 技术风险清单

| 风险 | 影响 | 应对方案 | 重新评估时机 |
|------|------|---------|-------------|
| 单进程部署且无反向代理，手机"添加到主屏"在 iOS / Android 上实际要求 HTTPS | PRD 场景 2 的"已添加到主屏"前提可能不成立 | 前置一层 Caddy（自带自动证书），应用侧无需改动；或接受仅内网/局域网使用 | 手机端实测无法添加到主屏时 |
| `ant-design-vue` 4.2.6 发布于 2024-11，latest 长期未更新 | 升级 Vue 4 或 TypeScript 大版本时可能无维护版本可用 | 组件用量控制在输入框、列表、分页、消息提示等稳定 API；升级前先小范围验证 | Vue / TypeScript 大版本升级时，或发现实测不兼容时 |
| `fastjson` → `fastjson2` 包名变更 | 遗漏 import 将导致编译失败；混用两代 API 易出隐蔽问题 | 全量搜索 `com.alibaba.fastjson` 并逐一替换；禁止同时保留两代依赖 | 升级完成后的首次 `mvn clean verify` |
| `MyBatis-Flex` 跨 7 个小版本升级 | 分页、`FULLTEXT` 相关度查询或实体映射行为可能变化 | 升级后重点回归分页与搜索；`map-underscore-to-camel-case: false` 须单独验证 | 升级后首轮联调 |
| `innodb_ngram_token_size` 为只读启动参数（默认 2），单字关键词无法命中 | 用户搜单个汉字时结果为空，易被误判为功能故障 | 应用层对单字输入回退 `LIKE` 兜底；前端提示输入 2 字以上 | 用户反馈搜不到内容时 |
| 决策 1 的 `FULLTEXT` 依赖 MySQL 8 的 ngram 插件行为，而 CI 使用 H2 | 全文检索相关逻辑无法在 CI 中真实覆盖 | 搜索逻辑在 H2 测试中降级为 `LIKE` 分支，真实行为由本机 MySQL 联调验证 | CI 与生产行为出现差异时 |
| 服务崩溃后不自恢复 | 站点在无人干预时长时间不可用 | 以 systemd 托管进程（仅托管，不引入反向代理） | 出现长时间不可用事故后 |
| 依赖版本一次性升级引入回归 | 升级后应用无法启动或测试失败 | 保留原版本号，失败即回退到最小干预方案（仅修 HikariCP） | 升级后 `mvn clean verify` 失败时 |

### 16. 明确不引入的技术

| 不引入 | 原因 |
|--------|------|
| Spring Security | 无注册、无邀请、无权限分级，角色能力全部用不上，反增过滤器链排障成本（决策 2） |
| JWT 之外的有状态会话方案 | 服务重启即掉线，与 30 天免登录冲突（决策 2） |
| Element Plus | 用户明确排除（决策 3） |
| Tailwind CSS / Nuxt / 现成模板 | 与"前端尽量少写"的目标相反，或与既有 Vite 骨架冲突（决策 3） |
| Meilisearch / Elasticsearch | 能力过剩，需额外进程、独立备份，并引入双写不一致（决策 1） |
| 向量数据库 / embedding 服务 | 与拒绝为局部能力引入重资产的方向冲突，结果不可解释（决策 5） |
| 任何链接抓取（Jsoup、Playwright、无头浏览器、SSRF 防护链） | 需求已改为只存 URL，服务端不对任意外部地址发起请求（决策 4） |
| Nginx / Caddy | 本版不引入反向代理；若后续需要 HTTPS 再单独前置（决策 6） |
| Docker / Docker Compose | 单机单进程，容器层与数据卷备份徒增心智负担（决策 6） |
| Microservices / 消息队列 / 缓存中间件（Redis 等） | 两人自用、量级极小，规模不适用，反而增加部署与排障复杂度 |
| 付费第三方服务 / 云端接口 | 违反 PRD"不引入付费第三方服务"的约束 |

本节与上述技术栈总览均会随决策变更而失效。某项被推翻后须核查其是否仍应保留在"不引入"清单中。

### 17. 关键陷阱清单

| 陷阱 | 正确做法 |
|------|---------|
| `vite.config.ts` 现有 `rewrite: path => path.replace(/^\/api/, '')` 会剥掉 `/api` 前缀，而后端 `context-path` 也是 `/api` | 删除该 `rewrite`，让 `/api/xxx` 原样转发到 `http://localhost:9090/api/xxx`；开发与生产行为须一致 |
| `HikariCP` 被 pom 显式钉在 4.0.3，与 Spring Boot 3.5.13 管理的 6.3.3 不符 | 删除该依赖的显式版本声明，交 Boot 管理（决策 7-R） |
| `fastjson 1.2.83` 升级到 fastjson2 后包名不同 | 全量替换 import 为 `com.alibaba.fastjson2`，并禁止两代并存；不得开启 `autoType` |
| MySQL `FULLTEXT` 未指定 `ngram` 解析器时中文分词失效，全文搜索形同虚设 | 建表须写 `FULLTEXT KEY ... (content) WITH PARSER ngram`；建完后用真实中文碎片验证一次命中 |
| `innodb_ngram_token_size=2` 下搜单个汉字返回空 | 应用层判断关键词长度，单字时回退 `LIKE %字%` 查询 |
| `application-dev.yml` 明文写有数据库口令（`root` / 明文密码） | 改为环境变量注入并加入 `.gitignore` 覆盖范围；JWT 签名密钥同样处理，绝不入库 |
| 时间流若用 `a-table`，手机端排版会崩坏 | 时间流、搜索结果一律用卡片列表，表格仅用于确有列语义的桌面场景 |
| `a-table`/Ant Design Vue 全量注册会显著增大打包体积 | 按需引入组件，或确认 Vite 侧 tree-shaking 生效 |
| 在同一事务里做任何外部请求（历史设计的链接抓取）会导致慢站点拖垮保存 | 本版已无外部请求；若未来重新引入抓取，必须放到保存之后异步执行并设超时 |
| 热力图若按天全表聚合，随总量增长会变慢 | 按天 `GROUP BY DATE(create_time)` 只取计数，并依赖 `create_time` 索引 |
| 详情页"相关碎片"查询若不过滤自身、不限数量 | 必须排除自身并 `LIMIT 5`，否则详情页明显变慢 |
| `spring.web.resources.cache` 与 `server.compression.enabled` 默认关闭，而本版无 Nginx | 在 `application.yml` 中显式开启静态资源缓存与 gzip，否则每次刷新重下资源 |
| 双人共用的统计（按创建日期分组计数）若按作者过滤 | 验收标准第 1 条与热力图均须统计两人全部碎片，不得加作者条件 |
