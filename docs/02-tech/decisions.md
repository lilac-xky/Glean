## 前置事实：既有骨架

仓库在需求确认前已初始化前后端骨架，下列内容属于既定事实，不作为开放选项重新决策，仅登记入技术栈总览：

- 后端：Spring Boot 3.5.13、Java 17、MyBatis-Flex 1.11.1、MySQL 8 驱动、Hutool 5.8.44、fastjson 1.2.83、HikariCP 4.0.3（显式指定）、H2（仅测试）

## 决策 1：数据存储与全文检索

- 决定：继续使用既有 MySQL 8，全文检索采用 InnoDB `FULLTEXT` 索引 + `ngram` 中文分词
- 日期：2026-11-09
- 理由：两人自用、每年数千条的量级，不需要独立检索服务；`FULLTEXT` 能同时提供中文分词与相关度打分，既满足「旧碎片能被记忆中关键词找到」的验收标准，也为详情页「相关碎片」的关键词相似度提供排序依据；仍在单个 MySQL 实例内，不引入双写一致性与额外常驻进程。
- 未采用的方案：
  - `LIKE %关键词%`：可用但不满足需求 —— 无分词、无相关度打分、无法为「相关碎片」提供相似度排序，且随数据增长必然全表扫描。
  - Meilisearch / Elasticsearch 独立检索服务：能力过剩；需额外安装、开机自启、独立备份，并引入「MySQL 写入成功但检索库写入失败」的不一致风险；单台云主机上多占常驻内存，与 PRD「低成本自部署、不引入付费第三方服务」的约束相悖。
- 已知代价 / 后续风险：
  - 建表需写 `FULLTEXT ... WITH PARSER ngram`。
  - `innodb_ngram_token_size`（默认 2）为只读启动参数，确定后不宜变更，否则需重建索引。
  - 单字关键词（如仅输入「库」）在 `ngram_token_size=2` 时无法命中，须由应用层回退 `LIKE` 兜底，并在前端引导用户输入 2 字以上关键词。
  - 中文停用词按内置规则处理，个别高频词可能不参与索引，须用真实碎片验证一次。
  - 语义同义词与拼写容错不支持。
- 复核时机：碎片总量超过 2 万条且搜索响应明显变慢；或用户明确要求搜错别字/同义词也能命中；或单字搜索成为高频用法且兜底方案仍不满足时。

## 决策 2：登录与会话

- 决定：自写 JWT 鉴权过滤器，不引入 Spring Security 过滤器链
- 日期：2026-11-09
- 理由：PRD 明确永久不做注册、邀请与权限分级，Spring Security 的角色与授权能力全部用不上，反而引入「过滤器链配置错误导致 401/403」这一最难排查的成本；项目只需「登录 → 签发 token → 后续请求识别是谁」三件事。JWT 无状态，服务重启不掉线，直接满足手机端 30 天免登录的验收要求。用户后端为主，手写过滤器可控性与可调试性优于配置 Security 链。
- 未采用的方案：
  - Spring Security + JWT：能力过剩，配置与排障成本明显更高，收益仅是「标准做法」这一形式上的规范。
  - Session + Cookie：服务重启或内存会话失效即掉线，与「登录态保持 30 天」冲突；跨域 Cookie 的 SameSite 配置在前后端分离加移动端场景下易出错。
- 已知代价 / 后续风险：
  - 密码哈希须使用 BCrypt（Hutool 提供），不得使用 MD5。
  - token 签发、过期校验、`userId` 注入请求上下文、CORS 预检 OPTIONS 放行均须自行实现并测试。
  - 签名密钥须置于配置且不得提交进 git；当前 `application-dev.yml` 中的数据库密码已明文硬编码，须一并改为环境变量。
  - JWT 无法主动失效（登出仅前端丢弃 token），本场景可接受。
- 复核时机：若未来需要多点登录管理、强制下线或引入第三位使用者并需要权限区分时，重新评估是否引入 Spring Security。

## 决策 3：前端 UI 形态

- 决定：采用组件库方案，组件库选定 Ant Design Vue 4.2.6（不使用 Element Plus）；页面结构与样式由项目自行编写，不引入现成模板或 SSR 框架
- 日期：2026-11-09
- 理由：
  - 用户前端为弱项并明确希望「尽量少写」，分页加载、消息提示、标签输入补全、筛选面板这四类均属组件库强项，手写成本更高。
  - 手机端高频动作只有「记一条」与「搜一条」，用输入框 + 列表 + 栅格配合窄屏断点即可覆盖，不需要专门的移动端组件库。
  - 热力图在任何方案下都需自绘，不应为它引入更重的方案。
  - 用户已在 Element Plus 与 Ant Design Vue 之间明确选择后者。
- 未采用的方案：
  - Element Plus：功能上与本场景接近，但用户明确排除，以其决定为准。
  - Tailwind CSS + 无头组件：样式自由度高，但表格、弹窗、日期选择需自行拼装，与「前端尽量少写」的前提相反，且用户 Vue 熟练度一般，类名体系上手成本偏高。
  - Vant 4：手机优先，但桌面端观感偏「手机页面放大」，而 PRD 场景 3（写博客时集中翻旧碎片）发生在电脑上。
  - Nuxt / 现成模板二次开发：与既有 Vite 单页骨架冲突，等同推倒重来；SSR 对两人自用项目无 SEO 收益；模板抽象层会成为后续改动负担。
- 已知代价 / 后续风险：
  - `ant-design-vue` 最新版为 4.2.6，发布于 2024-11，latest 标签长期未更新，社区活跃度与生态插件会逐渐落后；升级 Vue 或 TypeScript 大版本时可能无对应维护版本，需自行解决兼容问题。本项目所用组件集中在输入框、列表、分页、消息提示等稳定 API，风险可控，但须记录在风险清单中。
  - 默认样式偏企业中后台观感，需覆盖一层主题变量（主色、圆角、间距）以贴近轻量记录工具的气质，约需半天工作量。
  - 手机端窄屏适配须自行编写媒体查询；时间流不得使用 `a-table` 之类表格组件，须采用卡片列表。
  - 应按需引入以控制打包体积，避免全量注册。
- 复核时机：`ant-design-vue` 出现与当前 Vue / TypeScript 版本不兼容的实测问题；或项目升级到 Vue 4 时；或界面代码量明显超出预期，说明组件库选型未达到「少写」目的。

## 决策 4：链接的处理方式

- 决定：不抓取链接内容。只保存用户粘贴的 URL，列表中以解析出的域名作为展示标识，点击直接跳转原站点。
- 日期：2026-11-09
- 理由：用户明确提出「为什么要抓取，直接留一个链接，我自己点进去就好」。抓取需承担 SSRF 防护、反爬站点失败降级、超时控制与无头浏览器常驻内存等一整套成本，而收益仅是「链接可被标题关键词搜索到」；在两人自用、可用标签替代检索的场景下不划算。去掉抓取后，服务端不对任意外部地址发起请求，SSRF 风险整体消失。
- 连带的需求变更：PRD 由 v0.1 升至 v0.2，同步修改场景 2 流程、输入定义表（删除「链接标题与摘要」行）、补充约定、验收标准第 4 条、异常处理表（链接抓取失败 → 链接无法访问）、术语表。技术方案以 PRD v0.2 为准。
- 未采用的方案：
  - 只抓取 `<title>` 的轻量方案：成本低（约 50 行），但用户已明确不需要抓取，尊重其判断，不保留半套实现。
  - 静态抓取 + Playwright 兜底（上一轮的 C1）：用户此前倾向 C，但在理解抓取的实际收益后决定整体去掉；该方案所需的无头浏览器常驻内存与双端环境差异继续成为不采用理由。
  - Jsoup / Hutool 静态抓取：仅能拿到静态页面标题，遇到反爬与 SPA 站点仍需降级，收益不足以支撑引入。
- 已知代价 / 后续风险：
  - 未打标签的纯链接碎片，日后只能通过 URL 或域名被搜索到，正文关键词搜不到——这是本决策最主要的功能损失，须由标签习惯补足。
  - 用户若希望链接可被内容搜索，需自行在内容中补充关键词（PRD v0.2 已明确写入这一处理方式）。
  - 系统不探测链接是否可访问，失效链接不会提示，属预期行为。
- 复核时机：若用户反馈「存过的链接事后搜不到」，且标签未能弥补时，重新评估最轻量的 `<title>` 抓取方案；若链接类碎片的占比显著升高（例如超过总量三成），亦须复核。

## 决策 5：「相关碎片」推荐算法

- 决定：纯 SQL 加权打分，一次性查询返回结果，不在 Java 层另算。权重规则：
  - 标签交集数 × 3
  - 加上 `MATCH(内容) AGAINST(当前碎片关键词)` 的相关度分
  - 乘以时间接近衰减系数：30 天内 ×1.0、90 天内 ×0.5、更早 ×0.2

  候选集排除自身，结果取 top 5。
- 日期：2026-11-09
- 理由：PRD 已把排序依据写死为「标签交集 + 关键词相似度 + 时间接近」，本质就是一个加权公式，不需要更复杂的机制。依赖决策 1 的 InnoDB FULLTEXT，关键词相关度可直接从 `MATCH ... AGAINST` 取得，无需另建计算层。数千条数据下 SQL 一次扫描毫无压力。用户明确要求「先做简单的」。可解释性也重要：推荐不准时能立刻判断是标签权重过高还是时间衰减过快，这一点内存计算与向量方案都做不到。
- 未采用的方案：
  - Java 内存计算（取出候选集后在 Service 层用词频、IDF 算分）：对数千条数据属于过度设计，且把同一套排序逻辑拆到 SQL 与 Java 两处维护。
  - 词向量 / 向量数据库语义推荐：须引入 embedding 服务或本地模型，与决策 4 拒绝为局部能力引入重资产的方向冲突；云主机难承载；结果不可解释，调参困难。
- 已知代价 / 后续风险：
  - 只对字面相关有效。内容写「缓存」与写「cache」的两条碎片互不推荐。
  - 权重系数为初始经验值，须用真实使用数据校准，初期推荐结果可能不准。
  - 查询须排除自身并限制 top 5，否则详情页加载会变慢。
  - 依赖决策 1 的 ngram 分词，单字词无法参与相关度计算。
- 复核时机：用户实际使用两周后反馈推荐明显不准；或碎片总量超过 2 万条导致详情页查询变慢；或用户明确提出需要「换个说法也能推出来」的语义能力时。复核时优先调整权重系数，而非直接更换方案。

## 决策 6：部署与运行方式

- 决定：单进程部署。前端 `dist` 构建产物打包进后端 jar 的静态资源目录，云主机上以 `java -jar` 方式运行，由 Spring 内嵌 Tomcat 同时提供页面与接口。不引入 Nginx，不引入 Docker。
- 日期：2026-11-09
- 理由：用户明确选择最简方案，只需要一个进程、一条启动命令，不需要维护反向代理配置与容器编排。该选择可逆：应用本身只监听 HTTP 端口，日后若需要反向代理或 HTTPS，只需在其前面加一层 Nginx 或 Caddy，应用代码与构建产物无需改动。
- 未采用的方案：
  - Nginx + systemd（原推荐）：可顺手解决 HTTPS、静态资源缓存与同域部署，但需维护两份配置文件；用户判断当前不需要。
  - Docker Compose：环境一致性好，但为两人自用项目引入容器层与数据卷备份的额外心智负担。
- 已知代价 / 后续风险：
  - **手机「添加到主屏」在 iOS 与 Android 上实际要求站点为 HTTPS**，不加反向代理的情况下该能力可能受限或不可用。缓解路径：后续在应用前追加一层 Caddy（自带自动证书），应用侧无需改动；若用户接受仅在局域网或内网使用，则不受此限制。
  - 无反向代理后，静态资源缓存头、gzip 压缩须在 Spring 侧配置；`spring.web.resources.cache` 与 `server.compression.enabled` 需显式开启，否则每次刷新都要重新下载资源。
  - 服务重启期间站点完全不可用（数秒级）。两人自用可接受，须在更新时选低峰时段。
  - 服务端崩溃后不会自动拉起，须自行保证进程存活（建议以 systemd 或云厂商进程守护方式托管，仅托管进程，不引入反向代理）。
  - 安全组或防火墙须直接暴露应用端口，端口暴露面比走反向代理略大，须确保该端口仅用于本应用并保持依赖更新。
- 配套默认约定（可在实现阶段调整）：
  - 备份：`mysqldump` 每日一次，保留最近 7 份，落盘位置不与数据库数据目录同盘；恢复步骤写入 `README.md`。
  - 数据存放：沿用既有 MySQL 实例，库名由 `lilac-blog` 改为 `glean`（原库名为骨架遗留，与本项目无关）。
  - 更新方式：本地 `mvn package` 产出 jar 后上传，替换旧 jar 并重启进程。
- 复核时机：手机端添加到主屏无法完成且用户不接受折中方案时；或需要对外暴露、要求 HTTPS 时；或服务出现无进程守护导致的长时间不可用后。

## 决策 7：第三方依赖治理

> **本条已作废**（2026-11-09）。用户在同一轮内将选择由「最小干预（A）」改为「统一治理（B）」。
> 作废原因：A 仅修正 HikariCP 版本错配，保留 fastjson 1.2.83 等老版本；用户倾向于一次把可预见的依赖隐患排掉。
> 本记录保留以备追溯，当前生效的决策见「决策 7-R」。

- 决定：最小干预。仅修正 `HikariCP` 被显式降级的问题（删除 pom 中的显式版本声明，交由 Spring Boot 3.5.13 管理，管理版本为 6.3.3）；其余依赖保持现有版本不动，包括 `fastjson 1.2.83`、`Hutool 5.8.44`、`MyBatis-Flex 1.11.1`。
- 日期：2026-11-09
- 理由：用户选择最小改动，优先保证尽快开工，不在业务代码尚未编写时引入依赖迁移的额外风险。数据库连接池版本错配是最可能导致「应用起不来或连接池行为异常」的隐患，单独修掉即可，其余依赖当前均可正常工作。
- 未采用的方案：
  - 统一治理（fastjson 换 fastjson2、Hutool 与 MyBatis-Flex 升到最新小版本）：需改 pom 并复测，fastjson 换 2.x 还涉及 import 调整；用户判断当前不必要。
  - 移除 fastjson、统一使用 Spring 自带 Jackson（原推荐）：能少一个历史高危漏洞较多的依赖，且当前业务代码为空、改动成本最低；但用户选择保留现状，以其决定为准。
- 已知代价 / 后续风险：
  - `fastjson 1.2.83` 属 1.x 老分支（最新为 2.0.66），历史上出现过 `autoType` 反序列化高危漏洞。因本服务最终会暴露在公网，须在代码层面避免使用 `JSON.parseObject(str, Object.class)` 一类可触发 `autoType` 的写法，且不得开启 `autoType` 支持。
  - `MyBatis-Flex 1.11.1` 落后于最新的 1.11.8，其中可能包含缺陷修复，未升级意味着这些修复不会生效。
  - `Hutool 5.8.44` 落后 4 个小版本，风险低。
  - 以上依赖在业务代码中一旦广泛使用，后续升级成本会随时间上升。
- 复核时机：出现 fastjson 相关的安全公告且影响到本项目所用 API 时；准备将服务暴露到公网前，须重新评估 fastjson 与 MyBatis-Flex 的版本；或 `mvn` 依赖检查报出高危项时。

## 决策 7-R：第三方依赖治理（当前生效，取代决策 7）

- 决定：统一治理，一次性排掉可预见的依赖隐患。
  - 删除 pom 中 `HikariCP` 的显式版本声明，交由 Spring Boot 3.5.13 管理（管理版本 6.3.3）。
  - `fastjson 1.2.83` 替换为 `fastjson2`（`com.alibaba.fastjson2:fastjson2`，最新 2.0.66）。
  - `Hutool` 由 5.8.44 升至 5.8.48。
  - `MyBatis-Flex` 由 1.11.1 升至 1.11.8。
- 日期：2026-11-09
- 理由：用户选择一次把依赖隐患排掉。当前业务代码尚为空，依赖迁移成本处于最低点，此时升级不会牵动已有代码。`fastjson2` 在安全性上明显优于 1.x 分支，且 1.2.83 所属老分支已不再是主线；`HikariCP` 被显式钉在 4.x 与 Boot 3.5 管理的 6.3.3 不符，属明确的版本错配，必须修正；`MyBatis-Flex` 与 `Hutool` 若干小版本的修复可在升级中一并获得。
- 作废的原决策：决策 7（最小干预）。作废原因：用户判断只修连接池不足以排掉风险，倾向于一次性治理。
- 未采用的方案：
  - 最小干预（原决策 7）：修得少、改动小，但 fastjson 1.x 与 MyBatis-Flex 老版本的问题继续留存。
  - 移除 fastjson、统一使用 Jackson：依赖面最窄，但会放弃 fastjson2 在部分场景的性能优势，且需改动所有 JSON 调用点；本次升级到 fastjson2 已能覆盖安全诉求，故不选。
- 已知代价 / 后续风险：
  - `fastjson` → `fastjson2` 的**包名由 `com.alibaba.fastjson` 变为 `com.alibaba.fastjson2`**，api 虽高度兼容但 import 必须全量调整；现有骨架中若已引用 fastjson 的类需同步修改，否则编译失败。
  - 升级 `MyBatis-Flex` 1.11.1 → 1.11.8 跨 7 个小版本，需重点回归分页、`FULLTEXT` 相关度查询与实体映射；`map-underscore-to-camel-case: false` 的既有配置在升级后行为须验证一次。
  - 升级须同步复测 GitHub Actions 中的 `mvn clean verify`，确保 H2 测试仍能启动上下文。
  - 升级后仍需遵守：不得开启 fastjson2 的 `autoType` 支持。
- 复核时机：升级后若 `mvn clean verify` 或 H2 上下文启动失败，回退到原版本并改走最小干预；若 fastjson2 与现有 Jackson 配置出现序列化行为冲突，则改为统一使用 Jackson。
