## 2. MVP 定义

MVP 完成指两人能够走完以下完整流程：

```
登录 → 首页输入一句话回车 → 碎片立即出现在时间流顶部 → 换个关键词搜索 → 找到一周前那条 → 复制走
```

这是一条**闭环**：既能记住，也能找回，并且跑在真实的云主机上而不是本机。缺少"搜索"则碎片进得去出不来；缺少"时间流"则看不见是否记录成功；缺少"登录"则无法区分作者（PRD 验收标准第 5 条）；缺少部署则该闭环只在开发机上成立，不构成"可用版本"。

包含（P0，ISSUE-001 至 ISSUE-017）：

- 最高风险的两项探针验证（中文全文检索、UI 组件库可用性）
- 依赖治理与密钥环境变量外置（决策 7-R）
- 建表脚本、实体与 Mapper（含 `FULLTEXT ... WITH PARSER ngram`）
- 自写 JWT 鉴权、登录接口与过滤器（决策 2）
- 碎片创建、时间流分页、作者标识、链接域名展示（决策 4）
- 全文搜索（含单字 LIKE 兜底）与标签筛选
- 标签列表与输入补全接口
- 前端骨架、登录页、首页（快速记录 + 时间流）、搜索页
- 手机端窄屏适配与 10 秒闭环真机实测
- 前端产物打包进 jar、生产配置、systemd 托管、备份脚本、README
- v0.1 验收与真实数据试运行

明确排除：

| 排除项 | 原因 | 预计版本 |
|--------|------|---------|
| 单条详情页 | 碎片本身很短，卡片可直接显示全文与复制；详情页的主要价值是编辑入口与相关碎片，二者本就延后 | v0.2 |
| 编辑与删除碎片 | 用户明确列为第一版之后项 | v0.2 |
| 类型自动推断（代码特征判定） | 用户明确列为第一版之后项；v0.1 仅保留"整条为链接 → 链接"这一条规则 | v0.2 |
| 标签页（标签云 + 标签下时间线） | 用户选定的 MVP 闭环为搜索找回，标签浏览非必经路径 | v0.2 |
| 导出 Markdown | 同属场景 3，依赖标签页 | v0.2 |
| 相关碎片推荐 | 依赖详情页与真实数据量，初期数据不足以为推荐提供依据 | v0.2 |
| 活跃热力图 | 用户明确列为第一版之后项，且 PRD 六条验收标准中不含它 | v0.3 |
| 随机漫游 | 需积累一定数据量才有意义 | v0.3 |
| 网络异常本地暂存 | v0.1 先保证"保存失败不清空输入框"，完整的待发队列延后 | v0.3 |
| 手机"添加到主屏"（HTTPS / Caddy） | 单进程部署无反向代理，iOS / Android 实际要求 HTTPS | v0.3 |

| 周期性回顾、AI 摘要 | PRD 已明确排 V2，触发条件为 V1 连续跑满两周 | 未排期 |

## 3. 里程碑

### v0.1 · MVP

- 完成标志：两个账号分别登录后看到同一份时间流；在页面上输入一句话回车，10 秒内出现在列表顶部；用一周前碎片里的关键词能搜到它；粘贴一个链接能保存并以域名展示、点击跳转。应用以 `java -jar` 在云主机运行，重启后自动拉起。
- 包含 issue：ISSUE-001 至 ISSUE-017（P0 全部）
- 预计时间：约 23 周（按每周 5 小时，87 小时含 30% 缓冲）
- 演示方式：用手机与电脑各录一段 30 秒操作，覆盖"记录 → 时间流 → 搜索 → 跳转链接"；`systemctl restart` 后页面仍可访问
- 本版**不满足**的 PRD 验收标准：第 6 条（标签页一键导出 Markdown，随 v0.2 达成）；第 1 条（连续 14 天每天至少 1 条）自本版上线日开始计时，属使用期指标而非开发指标

### v0.2 · 场景 3 完整走通

- 完成标志：进入标签页 → 点某个标签 → 看到该标签下按时间倒序的全部碎片 → 点开一条看详情与相关碎片 → 点"导出 Markdown"得到可直接粘进博客编辑器的文本；碎片可编辑、可删除自己记的；两人同时改同一条时后保存者收到提示。
- 包含 issue：ISSUE-018 至 ISSUE-023（P1 全部 6 条）
- 预计时间：约 9 周（34 小时含缓冲），累计第 32 周
- 达成后 PRD 验收标准第 6 条闭环

### v0.3 · 打磨与运维增强

- 完成标志：首页有活跃热力图、每周能随手点开随机 5 条回顾、断网时记录不丢；站点有 HTTPS，手机可添加到主屏并以接近应用的方式打开；备份恢复已实际演练一次。
- 包含 issue：ISSUE-024 至 ISSUE-029（P2 全部）
- 预计时间：约 7 周（27 小时含缓冲），累计第 39 周

### v1.0 · 稳定版

- 完成标志：连续使用三个月无数据丢失、无阻塞性缺陷；依赖版本复核结论为"可继续使用"，或已完成升级。
- 预计时间：v0.3 完成后再观察一段实际使用，不预设工时
- v1.0 仅在用户明确宣布"正式版"时使用，平时按 v0.1 / v0.2 / v0.3 递增

## 4. 版本节奏建议

以下为建议，以项目实际情况为准，可随时调整。

```
时间轴（按每周 5 小时）：
第 1-2 周      探针          ngram 检索与 UI 组件库可用性定生死
第 3-11 周     v0.1 地基     依赖治理、建表、鉴权、前端骨架
第 12-18 周    v0.1 闭环     记录、时间流、搜索、两个页面
第 19-23 周    v0.1 上线     手机实测、打包、部署、验收
第 24-32 周    v0.2          详情与编辑、相关碎片、标签页、导出
第 33-39 周    v0.3          热力图、随机漫游、断网暂存、HTTPS、备份演练
其后           v1.0          稳定
```

定档依据：P0 共 17 条约 87 小时，按每周 5 小时计为 17.4 周，留 30% 缓冲后约 23 周。前两周单独留给两条探针——它们若失败，后面 15 条的写法会变，越早发现代价越小。

**风险**：ISSUE-001 与 ISSUE-002 都是"可能推翻整套方案"的验证，不是普通开发任务；ISSUE-015（真机 10 秒实测）与 ISSUE-016（systemd 托管）分别依赖真实手机与云主机，环境没准备好就会空转一周。

## 5. 关键路径与依赖

```
关键路径（59 h）：
001 ─► 004 ─► 005 ─► 007 ─► 008 ─► 010 ─► 011 ─► 014 ─► 015 ─► 016 ─► 017

前端支线（13 h，可由 B 并行接手）：
002 ─► 006 ─► 009 ─► 011

检索支线（9 h，与前端并行）：
001 ─► 012 ─┐
010 ─► 013 ─┴─► 014

前置无依赖（15 h，消化前三周零碎时间）：
001 / 002 / 003 三者互不依赖
```

- **关键路径**：001 → 004 → 005 → 007 → 008 → 010 → 011 → 014 → 015 → 016 → 017，共 59 小时。这条链上任一环延误，v0.1 整体顺延。
- **可并行支线 A（前端）**：002 → 006 → 009，共 13 小时。只依赖"登录接口的契约"，可在 007 完成前先用 mock 顶替，等 007 落地后替换。
- **可并行支线 B（检索与标签）**：012（6 h）与 013（3 h）都在 010 之后即可开工，与前端页面开发并行，最终在 014 汇合。
- **汇合点**：ISSUE-011（首页）需要 006、009、010 同时就绪；ISSUE-014（搜索页）需要 011、012、013 三者就绪。这两个节点是全项目依赖最密的地方，宜提前把 013 这类 3 小时的小项清掉，避免卡在 014 前。
- **无依赖可随时插入**：001、002、003 三条互不依赖，总共 15 小时，正好消化前三周的零碎时间。

## 7. 与上游文档的偏离说明

本排期在以下五处与 TECH-PRD / PRD 不一致，逐条说明原因，避免后续被误判为排期错误。

| # | 偏离内容 | 原因 |
|---|---------|------|
| 1 | 单条详情页由 MVP 移至 v0.2 | 用户选定的 MVP 闭环为"记录 → 时间流 → 搜索找回"，不含详情页。碎片内容本身很短，时间流卡片可直接展示全文并支持复制，场景 4 的"点开详情复制命令"在卡片内即可完成。详情页的核心价值（编辑入口、相关碎片）本就顺延，单独为它做一页不划算 |
| 2 | 标签页与导出 Markdown 移出 MVP，PRD 验收标准第 6 条因此在 v0.1 不满足 | 同为用户选定闭环的直接后果。须在 v0.1 发布说明中写明"标签页与导出随 v0.2 交付"，不得让使用者以为功能缺失是缺陷 |
| 3 | 类型自动推断降为 P1，v0.1 仅实现"整条为链接 → 链接" | PRD §5 补充约定要求"含代码块或命令行特征 → 命令·代码"。v0.1 先落「想法」默认值，属对 PRD 该行的临时偏离，v0.2 补齐。偏离期间不影响记录本身（类型可在后续编辑时补） |
| 4 | 建议移除 `server.servlet.context-path=/api`，改为接口统一 `/api/**` 前缀 | **编制排期时新发现的问题**：TECH-PRD §13 与 §17 按 `context-path=/api` 描述，但决策 6 要求前端 `dist` 打进同一个 jar。一旦如此，页面与接口共用 `/api` 前缀，静态资源（如 `/api/assets/x.js`）与接口命名空间重叠，首页 URL 会变成 `http://host:9090/api/`。ISSUE-006 第一步须定下 URL 归属；若采纳本建议，须回改 TECH-PRD §13 与 §17 陷阱表中的对应行 |
| 5 | 活跃热力图排在 v0.3（P2） | 用户明确列为可延后项；PRD 六条验收标准均不依赖它，PRD §6 亦已声明它"只反映活跃度，不承担知识库本体职责" |

另有一项**不构成偏离但需记录**：决策 6 已承认手机"添加到主屏"在无反向代理时要求 HTTPS，该能力因此排入 v0.3（ISSUE-027）。v0.1 上线后手机可正常使用浏览器访问，但"主屏图标"这一 PRD §10 平台约束可能暂时不成立。
