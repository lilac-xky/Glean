## P0 · MVP

MVP 闭环：**登录 → 输入一句话回车 → 碎片出现在时间流顶部 → 换个关键词搜到它 → 复制走**。P0 共 17 条、87 小时。

两条探针之后是三个阶段：地基（数据与鉴权）、闭环（记录与找回）、上线（部署与验收）。

### [P0] ISSUE-001 【探针】MySQL ngram 中文全文检索可用性验证

- 模块：数据 / 研究（独立 SQL 脚本 + 临时表，不进主系统）
- 描述：决策 1 把全文检索押在 InnoDB `FULLTEXT` + `ngram` 上，但"中文检索是否真的能命中"从未用真实碎片验证过。`innodb_ngram_token_size=2` 意味着单字无法命中，中文停用词按内置规则处理——这两点足以让"旧碎片能被关键词找到"这条验收标准落空。用一个下午证伪，远好过写完搜索页两周后才发现。
- 执行内容：
  1. 确认本机 MySQL 版本与 `innodb_ngram_token_size` 实际取值（`SHOW VARIABLES LIKE 'innodb_ngram_token_size'`）
  2. 建一张临时表 `probe_fragment`，`content` 列加 `FULLTEXT ... WITH PARSER ngram` 索引（该索引必须按名称显式指定）
  3. 灌入不少于 30 条贴近真实使用的碎片文本，覆盖：纯中文、中英混排、命令行片段（如 `gradle --offline build`）、含 URL、含单字关键词
  4. 用 8 至 10 个真实查询词逐个执行 `MATCH(content) AGAINST('词' IN NATURAL LANGUAGE MODE)`，记录命中与排序
  5. 单独验证单字查询（如搜「库」「包」）的实际返回，作为 LIKE 兜底的依据
  6. 记录 `LIKE '%词%'` 对照结果与两者耗时
- 验收标准：
  - [ ] 输出一张对照表：查询词 × 是否命中 × 排序位置 × ngram 与 LIKE 耗时
  - [ ] 双字及以上中文查询命中率不低于 8/10，且目标碎片出现在前 10 条内
  - [ ] 单字查询的实际行为已记录在案（命中或落空，不假设）
  - [ ] 给出明确结论：**采用 ngram**，或**须改用 LIKE + 应用层打分**（若后者，搜索类 issue 的估时按 +6 小时重估）
  - [ ] 结论写入 `docs/02-tech/` 下的验证记录，供 ISSUE-004 与 ISSUE-012 直接引用
- 依赖：无，不需要等工程骨架，为独立 SQL 脚本
- 估时：5 小时
- 技术依据：TECH-PRD 决策点 1、第 15 节风险表第 5 行、第 17 节陷阱表第 4、5 行
- 优先原因：该假设决定搜索、标签页检索与"相关碎片推荐"三处设计。若第 10 周才发现中文搜不出来，须重做 ISSUE-012、ISSUE-014，并推翻 ISSUE-004 的表结构。

### [P0] ISSUE-007 登录接口与 JWT 签发

- 模块：后端（`controller` / `service` / `utils`）
- 描述：按决策 2 自写登录。只有一件事：校验账号口令，签出一个 30 天有效的 token。不引入 Spring Security。
- 执行内容：
  1. `POST /api/auth/login`，请求体 `{username, password}`，返回 `{token, user:{id, displayName}}`
  2. 密码校验用 BCrypt（Hutool 已提供），不比对明文
  3. JWT 签发：`HS256`，载荷含 `userId` 与过期时间，有效期 30 天；签名密钥从环境变量读取
  4. 账号不存在与密码错误返回同一个错误码（`USER_OR_PASSWORD_ERROR`），不泄露账号是否存在
  5. `GET /api/auth/me`：根据 token 返回当前用户，供前端刷新页面时校验登录态
  6. 单测：正确口令通过、错误口令拒绝、token 可解析出 userId、过期 token 被判定失效
- 验收标准：
  - [ ] 正确账号口令返回 token，错误口令返回 `USER_OR_PASSWORD_ERROR`
  - [ ] 解析 token 得到的 userId 与登录账号一致
  - [ ] 把 token 的过期时间改为 1 秒后，`/api/auth/me` 正确返回未授权
  - [ ] 密钥缺失时应用启动即报错，不静默使用默认值
  - [ ] 四个单测全部通过
- 依赖：ISSUE-004、ISSUE-005
- 估时：5 小时
- 技术依据：TECH-PRD 决策点 2、第 11 节认证行；PRD 第 5 章（登录态保持 30 天）

- 描述：决策 5 的加权打分，纯 SQL 一次查询。依赖已有真实数据——这也是它排在 P1 而非 P0 的另一个理由：v0.1 只有种子数据时，无论如何调权重都看不出准不准。
- 执行内容：
  1. 实现 `score = 标签交集数 × 3 + MATCH(内容) AGAINST(当前碎片关键词) × 时间衰减`，时间衰减为 30 天内 ×1.0、90 天内 ×0.5、更早 ×0.2
  2. 排除自身，`LIMIT 5`
  3. `GET /api/fragment/{id}/related`
  4. 前端填入详情页"相关碎片"区，点进去可跳转
  5. 用真实数据人工抽查 10 条，记录推荐是否合理
- 验收标准：
  - [ ] 任一碎片能取到最多 5 条相关，且结果中不含自身
  - [ ] 无标签、无关键词共现时可返回空数组而不报错
  - [ ] 详情页加载时间无明显增加（< 500ms，本地环境）
  - [ ] 10 条抽查结果记录在案，作为后续调权重的基线
- 依赖：ISSUE-018、ISSUE-012
- 估时：6 小时
- 技术依据：TECH-PRD 决策点 5、第 17 节陷阱表第 10 行

### [P1] ISSUE-022 标签页

- 模块：后端 + 前端（`views/Tags.vue`）
- 描述：PRD 场景 3 的入口——进标签页、点一个标签、看到该标签下的全部碎片。
- 执行内容：

  3. 前端 `/tags` 列表页与 `/tags/:tag` 详情页
  4. 顶部放置"导出 Markdown"按钮（由 ISSUE-023 实现）
- 验收标准：
  - [ ] 标签云展示全部标签，次数越多越显眼
  - [ ] 点进某个标签能看到该标签下两人记录的全部碎片，按时间倒序
  - [ ] 分页可用
  - [ ] 无标签时的空状态提示不报错
- 依赖：ISSUE-013、ISSUE-011
- 估时：5 小时
- 技术依据：PRD 场景 3、第 6 章标签页行、第 9 章数据为空行

### [P1] ISSUE-023 导出 Markdown

### [P2] ISSUE-024 活跃热力图

- 模块：后端 + 前端
- 描述：PRD 第 6 章的输出项，用户明确延后。只统计"哪天记了几条"，不承担检索职责。
- 执行内容：
  1. `GET /api/stats/daily?days=180`：按 `GROUP BY DATE(create_time)` 只取计数
  2. 前端自绘方格热力图（GitHub 风格），移动端可横向滚动
  3. 不区分作者，统计两人全部碎片
  4. 依赖 `create_time` 索引，不得全表扫描
- 验收标准：
  - [ ] 每日计数与实际数据一致，可手工抽查 3 天
  - [ ] 统计未加作者过滤
  - [ ] 数据量增至 5000 条时接口仍在 200ms 内返回（可造数验证）
  - [ ] 手机宽度下可横滑查看，不撑破布局
- 依赖：ISSUE-017
- 估时：6 小时
- 技术依据：PRD 第 6 章活跃热力图行、第 9 章数据量超出预期行；TECH-PRD 第 17 节陷阱表第 11、12 行

### [P2] ISSUE-025 随机漫游

- 模块：后端 + 前端
- 描述：随机抽 5 条旧碎片，用来触发回顾。PRD 说明它需要一定数据量才有意义，故排在 P2。
- 执行内容：
  1. `GET /api/fragment/random?size=5`：随机取 5 条未删除碎片
  2. 首页提供一个入口按钮，弹层展示 5 张卡片，可继续"再来一批"
  3. 超时或数据不足 5 条时不报错
- 验收标准：
  - [ ] 每次返回 5 条（数据足够时），连续 5 次结果不全相同
  - [ ] 碎片不足 5 条时返回实际条数
  - [ ] 已删除碎片不出现
- 依赖：ISSUE-020
- 估时：3 小时
- 技术依据：PRD 第 6 章随机漫游行、第 9 章数据为空行

### [P2] ISSUE-026 网络异常时的本地暂存与恢复重试

- 模块：前端
- 描述：PRD 第 9 章要求"网络异常时提示内容已暂存在本地，恢复后提示重试，已输入的文字不得丢失"。v0.1 只做到"保存失败保留输入框内容"，本条把它做完整。
- 执行内容：
  1. 提交失败（网络错误，非业务错误）时把内容写入 `localStorage` 待发队列
  2. 提示"网络异常，内容已暂存在本地"
  3. 恢复联网（`online` 事件或下次打开页面）时提示"检测到 N 条未提交内容，是否重试"，由用户确认后重放
  4. 重放成功后清理队列
- 验收标准：
  - [ ] 断网提交后内容进入本地队列，提示文案与 PRD 一致
  - [ ] 恢复网络后收到重试提示，确认后成功入库
  - [ ] 关闭页面再打开，队列内容仍在
  - [ ] 业务错误（如内容为空）不进队列
- 依赖：ISSUE-011
- 估时：4 小时
- 技术依据：PRD 第 9 章网络中断行、第 10 章"无离线记录要求（断网时仅需保证已输入内容不丢失）"

### [P2] ISSUE-027 HTTPS 前置与手机添加到主屏

  4. 更新 README 的部署结构说明
- 验收标准：
  - [ ] 通过 HTTPS 域名访问正常，接口与静态资源均无混合内容告警
  - [ ] iOS Safari 可添加到主屏，点击图标以独立窗口打开
  - [ ] Android Chrome 出现安装提示，安装后可打开
  - [ ] HTTP 访问被重定向到 HTTPS
- 依赖：ISSUE-016
- 估时：7 小时
- 技术依据：TECH-PRD 决策点 6（已知代价第 1 条）、第 15 节风险表第 1 行、第 16 节"不引入 Caddy"的复核时机；PRD 第 10 章平台约束

  - [ ] 卡片行高与间距可让 5 条碎片在一屏内读完
  - [ ] 加载态与空状态在四处（首页、搜索、标签页、详情页）表现统一
  - [ ] 打包体积无明显增长
- 依赖：ISSUE-017
- 估时：4 小时
