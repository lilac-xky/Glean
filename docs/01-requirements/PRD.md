# 《Glean》产品需求文档

| 项 | 内容 |
|----|------|
| 项目代号 | Glean |
| 一句话描述 | 一个两人共用的技术碎片记录库：日常用一句话记下链接、命令、踩坑、想法、流程，之后靠搜索与标签找回，并能把某个主题下的碎片导出成博客草稿。 |
| 版本 | v0.2 |
| 日期 | 2026-11-09 |
| 状态 | 需求已确认 |
| 确认人 | 用户（本人及一位朋友） |

## 1. 产品概述

Glean 是一个给自己和朋友用的技术碎片记录库。核心动作只有一个：想到什么就记一条，不分类、不打草稿，几秒钟存进去。这些碎片平时看起来是流水账，但通过标签汇聚、全文搜索和相关推荐，会慢慢长出一个个主题页；写到某个主题时，一键把这些碎片按时间导出成 Markdown，就是一篇博客的原料。

它要解决的不是"知识管理"这个大词，而是三件具体的小事：记的时候不要因为要分类而放弃，找的时候不要因为散落在聊天记录和书签里而放弃，写东西的时候不要因为想不起来用过而重头再来。

## 2. 目标用户

| 角色 | 说明 | 技术背景 | 使用频率 |
|------|------|---------|---------|
| 记录者 A | 产品的主要提出者，负责后端方向，日常在电脑前开发与部署 | 开发者，熟悉命令行、数据库与接口调试 | 每天多次 |
| 记录者 B | 合作的朋友，负责前端方向，同样会遇到踩坑与链接收集 | 开发者，熟悉页面开发与浏览器调试 | 每天多次 |

两人共用同一份内容，互相可见。不做注册开放、不做成员邀请、不做权限分级。

## 3. 问题与痛点

- 当前做法：
  - 踩坑时随手发到微信收藏或文件传输助手，看到好文章就加进浏览器书签，命令和配置贴在备忘录里；
  - 试过用笔记类工具做知识库，建了目录、套了模板；
  - 写博客时凭记忆去翻，翻不到就重写一遍。
- 主要问题：
  - 散落各处，事后按关键词找不回来，等于没存；
  - 记录动作本身有摩擦（要打开页面、选分类、起标题），于是干脆不记，同样的坑重踩；
  - 笔记工具的分类与模板维护成本高于收益，坚持不过两周；
  - 记完之后从不回看，原料与成品之间断了链。
- 不解决的后果：
  - 时间被重复消耗在已经解决过的问题上；
  - 想写的东西写不出来，因为素材在三个月前就已经丢了；
  - 两个人各自踩各自的坑，经验不共享。

## 4. 典型使用场景

### 场景 1：调试中途顺手记一条

- 时机：工作日白天，正在调试一个部署问题时
- 终端：电脑浏览器
- 主体：记录者 A
- 流程：在页面上按下快捷键，输入框获得焦点 → 输入一句"nginx 反代 websocket 要加 Upgrade 头" → 回车 → 该条立即出现在首页时间流最上方，类型被自动判为"踩坑" → 全程不离开当前页面，不选分类、不写标题。整个过程从开始打字到看见结果在 10 秒以内。

### 场景 2：手机上刷到文章随手存

- 时机：通勤或休息时刷到一篇有价值的文章
- 终端：手机浏览器（已添加到主屏）
- 主体：记录者 B
- 流程：打开应用 → 把文章链接粘贴进输入框 → 系统识别出这是一个链接 → 点保存 → 链接以"链接"类型入库，显示域名与链接地址，点击可跳转到原站点。系统不抓取网页内容，标题如需保留由用户自行写在内容里。

### 场景 3：写博客时集中翻旧碎片

- 时机：周末准备写一篇关于缓存设计的文章
- 终端：电脑浏览器
- 主体：记录者 A
- 流程：进入标签页，点"redis"标签 → 看到该标签下按时间倒序排列的全部碎片（来自两个人的）→ 点开其中几条看详情与"相关碎片" → 觉得素材够了，点"导出 Markdown" → 得到一份按时间排序、带标签与来源链接的文本 → 复制到自己的博客编辑器里继续写。

### 场景 4：找一条记不清的旧内容

- 时机：突然要用某个几天前记下的命令
- 终端：电脑或手机
- 主体：两个人中任意一个
- 流程：进搜索页输入印象里的关键词"gradle 离线" → 结果列表出现若干条，含"gradle 离线编译一直失败"那条 → 叠加标签"部署"进一步缩小 → 点开详情，复制命令。若无结果，页面提示"试试别的关键词"，并给出一键清空筛选。

## 5. 输入定义

| 输入项 | 来源 | 提供方 | 格式 | 频率 |
|--------|------|--------|------|------|
| 碎片内容 | 手动录入（单行输入框，回车提交） | 记录者 A / B | 纯文本，允许含代码与换行 | 每天多次 |
| 碎片类型 | 手动选择，可留空由系统推测 | 记录者 A / B | 五选一：链接 / 命令·代码 / 踩坑 / 想法 / 流程 | 每次记录 |
| 标签 | 手动输入，可留空，从历史标签补全 | 记录者 A / B | 扁平文本标签，0～3 个 | 每次记录 |
| 链接地址 | 手动粘贴或随内容带出 | 记录者 A / B | http / https 地址 | 每次记录 |
| 账号登录 | 手动输入 | 记录者 A / B | 账号口令 | 首次登录，此后保持 30 天 |

补充约定：

- 必填项只有"内容"一项。类型、标签、链接均可留空，先存后补。
- 当整条内容本身就是一个 http(s) 地址时，系统自动按"链接"类型处理，并从地址中解析出域名用于列表展示。
- 系统不对链接发起任何网络请求，不抓取标题、摘要或正文。
- 类型留空时由系统按内容推测：整条为链接 → 链接；含代码块或命令行特征 → 命令·代码；其余 → 想法。保存后可在详情页改。
- 标签为扁平结构，不做层级；输入时从历史标签中补全。
- 验收指标：从开始打字到碎片出现在列表里，不超过 10 秒；登录态保持 30 天，不因重新登录而阻断记录。

## 6. 输出定义

| 输出项 | 形式 | 呈现位置 | 受众 | 是否需导出 |
|--------|------|---------|------|-----------|
| 首页时间流 | 倒序列表 + 顶部快速输入框 | 屏幕 | 记录者 A / B | 否 |
| 活跃热力图 | 按天计数、类似 GitHub 的方格图 | 屏幕 | 记录者 A / B | 否 |
| 标签页 | 标签云 + 该标签下碎片时间线 | 屏幕 | 记录者 A / B | 否 |
| 搜索结果 | 关键词命中列表 + 标签组合筛选 | 屏幕 | 记录者 A / B | 否 |
| 单条详情 | 内容、类型、标签、作者、相关碎片、编辑入口 | 屏幕 | 记录者 A / B | 否 |
| 随机漫游 | 随机抽取 5 条旧碎片 | 屏幕 | 记录者 A / B | 否 |
| 主题 Markdown 草稿 | 文本 | 屏幕（可复制）/ 文件 | 记录者 A / B | 是，Markdown |

补充约定：

- 每条碎片在列表与详情页标出作者与创建时间。
- 导出范围可以是全部碎片，也可以是某个标签下的碎片；按时间排序，含内容、标签与来源链接；系统只产出文本，不负责发布。
- 热力图只反映"哪天记了几条"的活跃度，不承担知识库本体的职责。

## 7. 验收标准

- [ ] 连续 14 天内，每天至少有 1 条碎片入库；该结果可通过"按创建日期分组计数"直接统计验证。
- [ ] 任意一条超过一周的旧碎片，可通过一个记忆中存在的关键词在搜索结果中被找到。
- [ ] 从在输入框打第一个字到该碎片出现在时间流中，耗时不超过 10 秒（在已登录、页面已打开的前提下计时）。
- [ ] 粘贴链接后保存成功，列表中以域名作为该条的展示标识，链接地址可点击跳转到原站点，全程不出现阻断性报错。
- [ ] 两人分别登录后看到的时间流内容完全一致，且每条碎片都能看出是谁记的。
- [ ] 任一标签页可一键导出为 Markdown 文本，内容按时间排序且包含该标签下的全部碎片。

## 8. 本版范围外

| 不做的事 | 原因 | 后续是否纳入 |
|---------|------|-------------|
| 周期性回顾（每周/每月新增统计） | 需先积累足够碎片才有意义 | 会做，排 V2 |
| AI 生成的周期摘要 | 锦上添花，非本版必需 | 会做，排 V2 |
| 双链 `[[标签]]` 式互相引用 | 对技术碎片而言"相关推荐"性价比更高 | 暂不做 |
| 推送到博客后台直接发布 | 导出 Markdown 已能满足"复制走"的需求 | 暂不做 |
| 开放注册、邀请、权限分级 | 固定两人共用一份内容，无此需求 | 永久不做 |
| 评论、点赞等互动 | 双人自用，无社交需求 | 永久不做 |
| 复杂富文本编辑器 | 与"10 秒记一条"的目标直接冲突 | 永久不做 |
| 多级分类树 | 分类应由标签事后涌现，不应在输入时前置 | 永久不做 |

### 8.1 后续版本路线图

| 版本 | 内容 | 触发条件 |
|------|------|---------|
| V1 | 记录、轻标签、全文搜索、相关推荐、热力图、随机漫游、导出 Markdown、双人共享与作者标识 | 现在 |
| V2 | 周期性回顾（每周/每月新增 N 条、涉及主题）、AI 周期摘要 | V1 连续跑满两周、每天都有碎片入库之后（即验收标准第 1 条达成） |

已约定的后续版本约束记录于此，防止后续版本偏离：

- 任何后续版本均不得引入输入时的强制分类或强制标签，输入必须保持"一个输入框 + 回车"。
- 任何后续版本均不得把热力图解释为知识库本体，它只表示活跃度。
- 若未来引入 AI 摘要，摘要须标注为机器生成，且不得替代原始碎片。
- 数据库中的每条碎片须始终保留作者字段，即便界面上不展示。

## 9. 异常与边界处理

| 情况 | 期望行为 |
|------|---------|
| 数据为空 | 首页显示引导句"记下第一条"，输入框自动获得焦点；标签页、热力图、随机漫游在无数据时给出同一类空状态提示，不报错 |
| 搜索无结果 | 提示"试试别的关键词"，并提供一键清空关键词与标签筛选的操作 |
| 数据格式错误 | 输入内容为空或只有空白时不允许提交，其余内容一律照存，不做格式校验拦截 |
| 处理过程中出错 | 保存失败时保留已输入内容不清空，提示"保存失败，请重试" |
| 数据量超出预期 | 时间流、搜索结果、标签页均分页加载；热力图按天聚合只取计数，不因碎片总量增长而变慢 |
| 网络中断 | 提示"网络异常，内容已暂存在本地"，恢复后提示重试；用户已输入的文字不得丢失 |
| 链接无法访问 | 碎片照常保存，链接原样保留，列表以域名作为展示标识；系统不探测链接是否可访问，不做失效提示 |
| 两人同时编辑同一条 | 后保存者收到"这条刚被对方改过"的提示，由本人决定是否覆盖 |
| 尝试删除对方的碎片 | 界面上不提供该入口；不出现权限报错页 |
| 同一链接被两人重复记录 | 两条都保留，不做自动去重，仅可在详情页看到"相关碎片"里出现同一链接 |

## 10. 约束条件

| 类型 | 约束 |
|------|------|
| 时间 | 无交付死线 |
| 预算 | 低成本自部署，开销控制在单台云主机量级，不引入付费第三方服务 |
| 平台 | 浏览器形态，电脑与手机均可用；手机端可添加到主屏并以接近应用的方式打开 |
| 既有系统 | 无既有系统需对接；产出的 Markdown 供用户复制到自己已有的博客使用 |
| 其他 | 数据归属两人自己，仅两人可访问，不做公开；不做注册推广；无离线记录要求（断网时仅需保证已输入内容不丢失） |

## 附录 A：术语对照

| 用户原话 | 对应含义 |
|---------|---------|
| 碎片 | 一条记录，含内容、类型、标签、链接、作者与创建时间 |
| 链接的展示标识 | 链接类型碎片在列表中显示其域名（如 `juejin.cn`），点击可跳转原站点，不抓取网页标题 |
| 低摩擦是生命线，发一条不能超过 10 秒 | 从开始打字到碎片出现在列表里不超过 10 秒，且不强制填类型、标签与标题 |
| 热力图只反映活跃度，不是知识库本体 | 热力图仅表示每日记录条数，不承担内容检索职责 |
| 靠"涌现"，不靠预先分类 | 不在输入时要求分类，主题由标签聚合事后形成 |
| 升格为 blog / 整理成 blog 草稿 | 把某标签下的碎片按时间导出为可复制的 Markdown 文本 |
| 随机漫游 | 随机抽取 5 条旧碎片，用于触发回顾 |
| 相关碎片 | 详情页底部按"标签交集 + 关键词相似度 + 时间接近"排序的推荐列表 |
| 只存，不分类 | 输入时只有内容必填，其余字段均可事后补 |
| 轻标签 | 扁平、可空、0～3 个、可自动补全的标签，无层级关系 |
